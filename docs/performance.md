# 性能测试计划

状态：已用于离线 SwiftShader 与 NVIDIA A40 对照，共 120 次正式运行。结果见 [实测报告](performance-report.md)。真实百度图层与主办方评测设备的验收仍未闭合；本轮报告观测值，不补写事后通过门槛。

## 对照方案

| 方案 | 行为 | 目的 |
| --- | --- | --- |
| B0：全量处理 | 全部获取与解析完成后按同一提交队列绘制 | 衡量全量等待对首次绘制的影响 |
| B1：简单分块 | 主线程惰性分块解析和提交，使用同一绘制内核 | 判断简单方案是否已经足够 |
| B2：Worker 分块 | 在 B1 基础上将解码放入 Worker，使用 Transferable | 分离异步解析带来的收益 |
| P：Worker 帧预算 | 在 B2 基础上加入批次间 3 ms 软提交预算 | 衡量预算的额外收益 |

四种模式共享相同绘制内核、Buffer 页和两批主线程提交队列。它们比较获取、解码与调度，不代表对 Buffer 优化本身的独立消融。保留简单基线优于复杂方案的结果。

## 固定条件

记录浏览器及版本、操作系统、CPU、GPU、内存、屏幕分辨率、设备像素比、网络限制、地图视角、数据种子和代码版本。

每组对比保持数据、可见要素、几何复杂度、更新频率和交互脚本一致。冷缓存与热缓存分别报告；初始加载与持续更新分别测试。

本轮业务响应 `Cache-Control: no-store`，每次运行新建浏览器 context；SDK、真实底图与跨运行缓存不进入本轮。相机轨迹由 elapsed time 的绝对函数定义。加载阶段按各自实际完成时间采样，因此帧样本长度及已到达几何会变化；另在全量提交后，使用相同轨迹与目标 2,000 ms 的稳态窗口，保存实际窗口时长。

测试档位逐步增加。点报告点数，线报告线要素数及总顶点数，面报告面要素数及三角形数；混合场景同时报告这三类数量。

## 指标定义

| 指标 | 测量定义与证据 |
| --- | --- |
| 首屏数据展示时间 | 从业务数据请求发起到第一批业务要素实际可见；地图初始化时间另报 |
| 持续加载速度 | 按时间窗记录下载字节、解析要素与提交要素，避免混用网络吞吐和处理吞吐 |
| 增量渲染效率 | 每批解析、传输、排队、GPU 上传及可见延迟；GPU 时间不可用时注明限制 |
| 最大支持规模 | 同时满足正确性、帧时间、内存和稳定性门槛的最大规模 |
| 加载期间 FPS | 覆盖初始、持续加载、完成各阶段，同时报告帧时间分位数 |
| 交互期间 FPS | 在固定缩放、平移、旋转序列中记录 FPS、帧时间与交互延迟 |
| CPU 使用率 | 使用可复现的浏览器或系统性能工具，注明进程范围和采样方法 |
| GPU 使用率 | 使用目标系统支持的 GPU 采样工具；缺失时记为不可用 |
| 内存 | 区分 JS 堆、页面或进程内存、估算 GPU Buffer 占用；记录峰值和释放后状态 |
| 调度与绘制开销 | 长任务、队列水位、主线程提交时间、Draw Call 与 Buffer 上传字节 |

第一批数据是否真正显示，需用截图、录屏或浏览器性能轨迹辅助验证，不能只以提交函数返回作为可见完成。

本轮持续记录的 `firstDrawMs` 仅为首次非零几何绘制调用时间，增量截图辅助证明已显示部分数据；它不能被改名为精确首屏呈现时间。`streamConsumedMs` 是应用读到 EOF 的时间，包含背压和暂停影响，不能作为纯网络传输完成时间。CPU/GPU 使用率保持不可用；JS 堆仅为可用时快照，Buffer 字节仅为图层分配值。

## 执行与报告

先验证正确性和测量链路，再运行规模测试。每个配置至少重复 5 次，保存逐次原始值，报告中位数、范围和帧时间 p95/p99。

报告包含数据生成参数、运行步骤、原始数据路径、错误与中断记录。将目标设备测试与开发环境结果分别标注；CPU/GPU 指标不可采集时保留缺口说明。

初始化阶段不创建虚构结果表。首次实测后再补充报告和原始数据索引。
